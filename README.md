# Кандидатогенерация для поиска услуг Авито (Recall@50)

Для каждого поискового запроса решение отбирает из корпуса в 189 212 объявлений до 50 кандидатов для ранжирования.
Всё считается локально на CPU, без внешних API. Результат - файл answer.csv с колонками query_id и answer, в answer записаны 50 item_id через пробел.

## Быстрый старт

```
pip install -r requirements.txt
# один раз скачать модель для локального запуска (дальше работает офлайн):
huggingface-cli download intfloat/multilingual-e5-small
# положить train.parquet, benchmark_queries.parquet, benchmark_items.parquet в папку data (или указать путь в --data)
python solution.py --data data --work work --out answer.csv
```

- Все промежуточные результаты кэшируются в папке, указанной в --work. Повторный запуск пропускает готовые стадии, чтобы пересчитать всё, удалите эту папку.
- Полный прогон с нуля на 6-ядерном процессоре без GPU занял 97 минут: лемматизация около 3 минут, нейросеть на кликах около 7, кодирование e5 (объявления пула около 22 минут, объявления train для адаптера около 35), обучение адаптера около 6, кандидаты и признаки около 11, ранкер около 10, инференс на бенчмарке около 2.
- Запуск без флагов даёт итоговый файл (на платформе Recall@50 = 0.903). Необязательные флаги: --with-quality добавляет признаки качества и популярности объявления (на платформе оказалось хуже, см. раздел про варианты), --no-adapter отключает адаптер e5 (быстрее, немного хуже), --debug запускает проверку работоспособности кода на маленькой выборке (результат не для сдачи).
- Все зерна случайности зафиксированы (SEED = 42, torch.manual_seed, deterministic у LightGBM), повторный запуск даёт тот же answer.csv (см. раздел про воспроизводимость).

## Идея решения

Решение работает в три шага. Сначала для запроса собираются кандидаты из нескольких каналов: лексический поиск, три плотные модели, память по логам и чистый текст без приоров. Затем для каждой пары запрос-кандидат считаются признаки. В конце LightGBM-ранкер выбирает 50 лучших.

Главная идея: пользователь почти всегда выбирает объявление рядом с локацией поиска, но id локации поиска и id локации объявления не совпадают напрямую. Связь между ними выучивается по кликам и работает как приор. Одно это поднимает Recall@50 у BM25 с 0.36 до 0.83, остальные компоненты добавляют ещё около 9 п.п.

Всё, что учится на кликах train (нейросети, адаптер, статистики), обучено на одной части запросов, а ранкер обучен на других запросах train, которые этим моделям не показывались. Иначе признаки нейросетей на обучении ранкера были бы подсмотренными и не походили бы на бенчмарк.

## Данные и признаки

### Какие данные использованы

| Данные | Как использованы |
|---|---|
| train.parquet, 497 673 пары запрос-объявление | Обучение нейросети и адаптера; статистики по кликам (вероятность локации, память по логам, центры локаций, микрокатегории); запросы для обучения и проверки ранкера |
| benchmark_items.parquet, 189 212 объявлений | Пул поиска: индексы BM25 по заголовку, параметрам и описанию, эмбеддинги, локация, координаты, микрокатегория |
| benchmark_queries.parquet, 2 452 запроса | Текст запроса, локация поиска, фильтры |

Не используются: search_is_delivery_search (в бенчмарке всегда 0), search_category (в train почти всегда 114, в бенчмарке у 9% запросов 0, поэтому признак ненадёжен; используется только чтобы отобрать запросы категории 114 при разбиении), item_category_id (у 99% корпуса одно значение), сам item_id.

Признаки качества объявления (цена, рейтинг, число отзывов, флаги скрытого телефона и запрета сообщений) и популярность объявления в логах по умолчанию тоже не используются, причина описана в разделе про варианты.

### Что выяснилось о данных и как это повлияло на решение

- Объявления train почти не пересекаются с корпусом: в корпусе есть 18 142 объявления train (5.3%), а из корпуса в train встречалось 9.6%. Поэтому объявления нельзя запомнить, нужно сопоставлять тексты. Память по логам работает как второстепенный канал: в валидации она находит только 1.6% положительных объявлений.
- Локация. Локация объявления совпадает с локацией поиска в 83% кликов; у региональных локаций поиска точных совпадений нет вообще. Выученная по кликам вероятность локации объявления при заданной локации поиска покрывает 97.5% кликов (оценка на отложенной половине). У 17% запросов бенчмарка в корпусе нет ни одного объявления с точно такой же локацией, так что жёсткий фильтр по локации дал бы потолок около 83%, поэтому локация используется как мягкий приор.
- Фильтры. Если в фильтре задан вид услуги, у 98% выбранных объявлений он совпадает, для типа услуги это 95%. Фильтр почти жёсткий, но у 63% запросов бенчмарка его нет.
- Текст. Описание объявления информативнее заголовка (Recall@50 у BM25 только по описанию 0.33, только по заголовку 0.30, только по параметрам 0.11), поэтому индексируются все три поля. У 5% выбранных объявлений с запросом нет ни одного общего слова, для них нужны плотные модели.
- Устройство бенчмарка. Это один случайный запрос на уникальный текст: запросы длиннее, чем в среднем по строкам train (3.2 слова против 2.5), 37% текстов уже встречаются в train, у 9% запросов категория равна 0, а фильтры есть у 37% против 67% в train. Валидация построена так же.
- Перекос обучающих данных. Часть строк train приходится на очень частые запросы (47% строк - на тексты, встречающиеся 100 и более раз, один текст - 6 540 раз), а отдельные объявления повторяются до 188 раз. Пары для обучения нейросетей поэтому дедуплицированы по (текст, объявление), а в потере не учитываются ложные негативы.

### Признаки ранкера

Итоговая модель использует 46 признаков пары запрос-объявление:

| Группа | Признаки | Зачем |
|---|---|---|
| Оценки BM25 (11) | BM25 по заголовку, параметрам и описанию по отдельности и суммой, нормировка на сумму IDF слов запроса, значение относительно лучшего в запросе, ранг по чистому тексту, число объявлений пула, совпавших с запросом | Поля несут разный сигнал; нормировки позволяют сравнивать оценки запросов разной длины и общности |
| Локация (5) | вероятность локации объявления при локации поиска, точное совпадение локаций, число объявлений пула в локации, число кликов из локации поиска в логе, расстояние до центра локации поиска | Главный сигнал данных; расстояние сглаживает случаи вне выученной связи; число объявлений показывает, насколько локация плотная |
| Фильтры (2) | совпал ли вид услуги (фильтра нет, совпал, не совпал), доля слов фильтра в параметрах объявления | Фильтр почти жёсткий; в ранкере вес небольшой, потому что то же заложено в приорах каналов |
| Нейросети и e5 (13) | косинус запроса и объявления, логарифм вероятности микрокатегории объявления по запросу, уверенность классификатора, отклонение косинуса от лучшего в запросе, ранг по косинусу | Близость по смыслу там, где слова не совпадают; микрокатегория отсекает объявления другого типа услуги |
| Формулы каналов и ранги (8) | оценка канала с приорами и ранг кандидата внутри запроса для BM25 и каждой плотной модели | Сжимают знание каждого канала в одно число и показывают, где кандидат сильнее |
| Память по логам (3) | сколько раз по тому же тексту кликали это объявление, то же с учётом локации, встречался ли текст в логах | Клик по тому же тексту - прямой сигнал, но он применим редко |
| Свойства запроса и текста (4) | число слов и длина запроса, длина заголовка и описания | Позволяют ранкеру по-разному вести себя на коротких и длинных запросах |

По суммарному приросту в итоговом ранкере ранги каналов дают 73%, оценки BM25 8%, локация 7%, формулы каналов 5%, косинусы нейросетей 5%, остальные группы меньше 1% каждая.

## Модели и алгоритмы

| Компонент | Что делает и почему выбран |
|---|---|
| Лемматизация pymorphy3 | Приводит слова к начальной форме, чтобы запрос ремонт квартир находил ремонт квартиры |
| BM25 с приорами (модуль cg/bm25.py) | Точное совпадение слов по трём полям, параметры k1 = 1.2, b = 0.75. К оценке добавляются логарифм вероятности локации и штраф за несовпадение вида услуги; веса приоров подобраны перебором на валидации |
| Двухбашенная нейросеть (cg/twotower.py) | Учится на кликах train: на входе TF-IDF признаки слов, пар слов и символьных n-грамм (устойчиво к опечаткам), на выходе вектор из 128 чисел. Башня объявления учитывает заголовок, параметры и микрокатегорию. Потеря InfoNCE по батчу из 2048 пар с маской ложных негативов и обучаемой температурой, плюс вспомогательная классификация микрокатегории по запросу. 6 эпох на 410 672 уникальных парах, около 7 минут на CPU |
| e5-small без дообучения (cg/e5.py) | Предобученная intfloat/multilingual-e5-small (open-source, лицензия MIT), эмбеддинги из 384 чисел. Даёт семантику для слов, которых нет в train: 90% объявлений корпуса в train не встречались |
| Адаптер e5 (cg/e5.py) | Две небольшие MLP-башни (384, 768, 384) с остаточными связями поверх замороженных эмбеддингов e5, дообученные на кликах тем же InfoNCE, плюс классификация микрокатегории. Выходной слой обнулён, поэтому обучение стартует с исходной модели. Лучший одиночный канал: Recall@50 с приорами 0.833 против 0.810 у нейросети и 0.764 у e5 без дообучения. Дообучение всей e5 на CPU слишком медленное, адаптер обучается за 6 минут |
| Память по логам | Объявления пула, на которые кликали в train по тому же лемматизированному тексту запроса |
| Чистый текст | Топ-40 по BM25 и по косинусу каждой плотной модели без приоров. Ловит клики вне выученной связи локаций |
| Объединение кандидатов | Из BM25 берётся 300 кандидатов, из каждой плотной модели 150, плюс чистый текст и память. Кандидат отбрасывается, если он не входит в топ-150 ни одного канала с приорами, в топ-40 ни одного канала по чистому тексту и не найден памятью. В среднем остаётся 430 кандидатов на запрос |
| LightGBM-ранкер (cg/ranker.py) | Постановка LambdaRank: сравнивает кандидатов внутри одного запроса. Объединяет разнородные сигналы, обучается на CPU за минуты. 63 листа, скорость 0.05, минимум 200 объектов в листе, L2 = 10, ранняя остановка по NDCG@50 на 4000 запросах. Итоговая модель обучена на 23 000 запросах (обучающие и валидационные) с числом деревьев на 10% больше, чем нашла ранняя остановка |

Гиперпараметры ранкера почти не влияют на результат: перебор числа листьев, доли признаков и регуляризации дал разброс в пределах шума. Другие целевые функции оказались не лучше: pointwise чуть хуже, rank_xendcg заметно хуже.

## Проверка качества до отправки

Локальная валидация. Из train взято 3000 запросов, по одному случайному на уникальный текст: так устроен бенчмарк (37% его текстов встречаются в train, в валидации 38%). У 30% запросов фильтры обнулены, потому что в бенчмарке они есть у 37% запросов. Положительные объявления этих запросов добавлены в корпус, как в бенчмарке, а сами запросы исключены из обучения нейросетей, адаптера и статистик. Ранкер обучен на других запросах, а ранняя остановка идёт на 4000 запросов из его обучающей части, поэтому валидационные запросы не участвуют ни в одном обучении, по которому считается оценка. Итоговая модель затем переобучается на обучающих и валидационных запросах вместе, но оценка получена до этого шага.

Метрика. Recall@50 считается как в ТЗ: для каждого запроса берётся доля его положительных объявлений среди выбранных 50 (положительные, не попавшие в кандидаты, считаются промахами), затем среднее по запросам.

Порядок проверок:

1. Данные. У 18 142 объявлений, которые есть и в train, и в корпусе, значения полей совпадают на 100%, дрейфа между выгрузками нет. При этом по рейтингу, отзывам, цене и флагам объявления train отличаются от объявлений корпуса (AUC 0.59), что позже объяснило завышение локальной оценки.
2. Пошаговое добавление компонентов (таблица ниже). Компонент оставлялся, только если давал прирост выше разброса между запусками.
3. Разбор потерь по типам и срезам (следующий раздел).
4. Проверка на утечку источника объявления: сравнение Recall@50 для положительных из корпуса и из train.
5. Пересчёт оценки на состав запросов бенчмарка.
6. Проверка формата файла скриптом check_answer.py: набор query_id совпадает с бенчмарком, нет повторов, не больше 50 объявлений, все item_id из корпуса и записаны 16 символами 0-9a-f, нет пустых ответов, файл в UTF-8 без BOM; скрипт предупреждает, если переводы строк CRLF.
7. Воспроизводимость и запуск в чистой папке (см. раздел про воспроизводимость).
8. Проверка на платформе: 0.903.

| Вариант (признаки самого объявления - качество и популярность - не используются, кроме последней строки) | Recall@50 на валидации |
|---|---|
| BM25 (заголовок, параметры, описание) | 0.361 |
| плюс приоры локации и вида услуги | 0.827 |
| плюс LightGBM по лексике и приорам | 0.852 |
| плюс двухбашенная нейросеть и память по логам | 0.904 |
| плюс e5-small без дообучения как ещё один канал | 0.913 |
| плюс адаптер e5 на кликах, текстовые каналы без приоров, отсечение слабых кандидатов (итоговый вариант, на платформе 0.903) | 0.916 |
| плюс признаки качества и популярности объявления (флаг --with-quality; на локальной валидации лучше, на платформе хуже) | 0.9225 |

Цифры взяты из полного прогона solution.py. В экспериментах те же конфигурации давали 0.917 и 0.924, то есть разброс между запусками около 0.2 п.п.

Ограничения оценки. Несколько весов приоров подбирались по этой же валидации, поэтому её оценка может быть чуть оптимистичной. Положительные объявления валидации взяты из train, а остальные из корпуса, что при использовании признаков самого объявления завышает оценку (см. раздел про варианты). Независимую оценку дала платформа.

Разница между локальной оценкой (0.916) и платформой (0.903) объясняется в основном составом запросов. В бенчмарке заметно больше запросов по самым крупным локациям поиска (Москва, Санкт-Петербург, общероссийский и региональный поиск): 31% против 25% в валидации. На них Recall@50 ниже на 14 п.п. (0.81 против 0.95). Пересчёт локальной оценки на состав бенчмарка даёт 0.908, платформа показала 0.903.

## Анализ ошибок

Потери разбирались дважды: на первой рабочей версии (BM25 с приорами, Recall@50 0.83) и на итоговой модели. Ниже найденные типы ошибок и принятые меры.

Положительное объявление вне выученной связи локаций. Что нашёл: у 3.5% положительных объявлений локация не входит в выученную связь с локацией поиска, на первой версии они терялись целиком. Эти объявления разбросаны географически (медиана расстояния до центра локации поиска 191 км, ближе 50 км только 22%), поэтому расширением радиуса проблему не решить. Что сделал: добавил каналы чистого текста без приоров. Они ловят 40% таких объявлений в топ-30 против 33% у всех положительных, потому что у них обычно сильное текстовое совпадение. В итоговой модели вне кандидатов из-за этого остаётся 1.2% положительных. Расстояние добавлено в ранкер как признак.

Нет общего слова с запросом. Что нашёл: 5.2% положительных на первой версии (синонимы, морфология, опечатки: уроки пианино и преподаватель по фортепиано). Что сделал: добавил плотные модели, обученные на кликах, и предобученную e5. Покрытие кандидатов выросло с 0.893 у BM25 с приорами до 0.958 у объединения всех каналов.

Нужное объявление найдено, но стоит ниже 50 места. Что нашёл: 9.3% положительных на первой версии, медианный ранг 140. Что сделал: заменил ручную формулу на LightGBM-ранкер по признакам всех каналов, Recall@50 вырос с 0.83 до 0.92.

Крупные локации поиска. Что нашёл: Recall@50 0.81 против 0.95 в остальных, покрытие кандидатов 0.91 против 0.97 (для общероссийского поиска 0.86, для регионального 0.88). В крупных городах тысячи одинаковых по смыслу объявлений, а выбор определяется тем, чего нет в данных: фото, позицией в выдаче, точным положением пользователя. Что сделал: проверил дополнительные признаки (пары слов, отдельное поле адреса, покрытие слов заголовка, признаки качества), они не дали прироста или оказались ненадёжными; принял это как предел данных и учёл при оценке ожидаемого результата на бенчмарке.

Конкретные промахи в крупных городах. Что нашёл: при ручном разборе выяснилось, что слово без входит в список служебных слов, поэтому запрос аренда микроавтобуса без водителя находит и объявления с водителем. Ещё один случай: в запросе покос травы воскресенск город указан прямо в тексте, а поиск идёт по Москве. Что сделал: для названий мест в запросе проверил отдельное поле адреса, прироста нет. Потерю отрицания не исправлял: для этого нужно пересчитать все этапы (около полутора часов), а ожидаемый эффект небольшой.

Промахи вне кандидатов на итоговой модели. Что нашёл: положительные, не попавшие в кандидаты, составляют 3.6% (119 из 3319). Из них 47% лежат в выученной связи локаций и совпадают с запросом по словам, но теряются среди тысяч похожих; 29% вне выученной связи, но совпадают по словам; 20% в выученной связи, но общих слов нет (синонимы); 3% не подходят ни под что. Что сделал: ничего не менял. Такие объявления лежат глубоко среди одинаковых по смыслу, и увеличение числа кандидатов вряд ли поднимет их в топ-50 (эту гипотезу отдельно не проверял).

Слабые срезы. Что нашёл: Recall@50 итоговой модели на валидации по срезам:

| Срез | Доля запросов | Recall@50 |
|---|---|---|
| одно слово в запросе | 4.6% | 0.889 |
| два слова | 31.1% | 0.911 |
| три слова | 32.4% | 0.920 |
| четыре слова и больше | 31.8% | 0.921 |
| фильтры есть | 37.1% | 0.926 |
| фильтров нет | 62.9% | 0.911 |
| текст запроса встречался в train | 43.1% | 0.930 |
| текст запроса новый | 56.9% | 0.906 |
| крупные локации поиска | 24.8% | 0.810 |
| остальные локации | 75.2% | 0.951 |
| одно положительное объявление | 94.4% | 0.923 |
| два и больше положительных | 5.6% | 0.807 |

Что сделал: слабые срезы (короткие запросы, запросы без фильтров, несколько положительных объявлений) учтены в оценке, отдельных мер не принимал.

Перекос обучающих данных. Что нашёл: часть строк train приходится на очень частые запросы, отдельные объявления повторяются до 188 раз. Что сделал: пары для нейросетей дедуплицированы по (текст, объявление), в потере InfoNCE маскируются ложные негативы (тот же запрос или то же объявление на другой позиции батча).

Расхождение бенчмарка и train. Что нашёл: у 9% запросов бенчмарка категория равна 0 (в train таких 34 строки), фильтры есть у 37% против 67% в train, запросы длиннее, тексты уникальны. Что сделал: не использую категорию как признак, в валидации у 30% запросов фильтры обнулены, валидация построена по одному запросу на уникальный текст.

Завышение локальной оценки признаками объявления. Что нашёл: признаки качества и популярности улучшали валидацию (0.9162 до 0.9225), но именно они выдавали источник объявления: популярность в логах в среднем 0.44 у объявлений из train против 0.11 у корпусных, а качество объявлений двух выборок различается (AUC 0.59). Что сделал: исключил эти признаки из итогового варианта. Платформа подтвердила выбор: вариант без них набрал 0.903 и оказался лучше варианта с ними. На положительных объявлениях из корпуса и из train итоговая модель ведёт себя одинаково (0.922 и 0.925), то есть заметной утечки источника у неё нет.

Формат файла. Что нашёл: pandas на Windows записал переводы строк CRLF, из-за чего при наивном разборе к последнему item_id строки добавился бы лишний символ и объявление не засчиталось бы. Что сделал: перевод строк LF в solution.py, предупреждение о CRLF в check_answer.py, защита файла от подмены окончаний строк в .gitattributes.

## Варианты и проверка на платформе

Локальная валидация имеет известную слабость: положительные объявления валидации взяты из train, а остальные объявления из корпуса бенчмарка, поэтому они различаются источником (у объявлений из train в среднем больше отзывов и кликов в логах). Признаки самого объявления могут выдавать источник и завышать локальную оценку.

| Вариант | Recall@50 на валидации | Платформа |
|---|---|---|
| Без признаков качества и популярности (по умолчанию) | 0.9162 | 0.903 |
| Флаг --with-quality: плюс рейтинг, отзывы, цена, флаги контактов, популярность объявления в click-логе | 0.9225 | хуже итогового варианта |

На платформе лучше отработал вариант без этих признаков, что согласуется с объяснением выше. Внутри локальной валидации признаки качества сами по себе не давали ничего (0.9154 против 0.9162), а весь выигрыш в 0.6 п.п. приходился на популярность объявления в click-логе (признак pop_base). Этот признак сильнее всего выдаёт источник: в среднем 0.44 у объявлений из train против 0.11 у корпусных. На положительных объявлениях из корпуса (единственный честный аналог бенчмарка, но всего 244 штуки) Recall@50 итоговой модели 0.922, у объявлений из train 0.925, то есть заметной утечки у итогового варианта нет. Поэтому итоговое решение использует только содержательные признаки: текст, локацию, фильтры, нейросети и память по логам.

## Воспроизводимость

Стадии solution.py проверены повторными запусками с теми же входными данными и зёрнами случайности, результаты сравнивались в ходе разработки:

| Проверка | Результат |
|---|---|
| Обучение двухбашенной нейросети (повторный запуск, эмбеддинги объявлений) | совпадает побитово |
| Обучение адаптера e5 (повторный запуск, эмбеддинги объявлений) | совпадает побитово |
| Кодирование e5 одного и того же списка в двух разных процессах | совпадает побитово |
| Стадии 5-7 (кандидаты, ранкер, answer.csv) повторно из кэша | итоговый файл совпадает побайтово |
| Обучение ранкера и итоговый файл (без флагов) | повторный запуск даёт побайтово тот же файл, он совпадает с загруженным на платформу (0.903) |
| Весь конвейер в режиме --debug в чистой папке только из файлов репозитория | все семь стадий проходят без ошибок |

После проверок единственное изменение кода - переводы строк в answer.csv теперь LF вместо CRLF Windows, чтобы последний item_id строки не получал хвостовой символ возврата каретки при наивном разборе. Содержимое ответов при этом побайтово прежнее.

Замечание: sentence-transformers сортирует тексты по длине, поэтому состав батчей (и паддинг) зависит от всего списка. Результат кодирования e5 воспроизводится при кодировании того же списка в том же порядке, как в solution.py, а не для его подмножества.

## Что не сработало (проверено на валидации)

- Трудные негативы в батчах и добавление описания в башню объявления нейросети: канал стал хуже (Recall@50 0.795 против 0.810).
- Дополнительные текстовые признаки (пары слов, отдельное поле адреса, покрытие слов заголовка): прирост 0.0004, не вошли.
- Ансамбль нескольких ранкеров и подбор параметров LightGBM: в пределах шума. Другие целевые функции: pointwise чуть хуже, rank_xendcg заметно хуже (Recall@50 0.894 против 0.917 на подвыборке).
- Более широкий адаптер e5 и другая температура: без выигрыша.
- Вторая нейросеть с описанием как дополнительный канал: прирост 0.14 п.п., в пределах шума, поэтому не вошла.

## Используемые open-source компоненты

pymorphy3 (лемматизация), scikit-learn, scipy, numpy, pandas, pyarrow, PyTorch, LightGBM, sentence-transformers и модель intfloat/multilingual-e5-small (лицензия MIT, запускается локально на CPU, веса скачиваются один раз и дальше читаются из локального кэша). Внешние API не используются. Ответы под конкретные query_id не хардкодятся, разметка бенчмарка вручную не восстанавливается.
